Rihanyo

A multi-agent, AI-powered appointment booking assistant that connects patients with medical practices through natural conversation. Built entirely on free-tier infrastructure as a solo student project, with a fallback chain across five AI providers.

Source Code Demo Video

Overview

Rihanyo is built around two sides of the same problem: making it easy for a practice to register and receive appointment requests, and making sure the admin is not stuck manually reading through spam or irrelevant submissions. New requests are automatically screened by an AI filter before they are surfaced to the admin dashboard.

The platform includes a chatbot receptionist that greets visitors, answers common questions, and routes or books appointment requests automatically. A WhatsApp AI receptionist is in development to allow patients to book via WhatsApp Business API. Location-based search lets users find the closest registered practice.

Built entirely on free-tier services as a solo student project with no budget for paid API access, Rihanyo uses a fallback chain across five AI providers (Cerebras, OpenRouter, Hugging Face, Groq, Gemini) so if one runs dry the system quietly moves to the next without the patient ever noticing a gap in service.

Key Features

Practice Registration

Practices can sign up and register their details including location, specialties, and contact information through a streamlined onboarding flow.

AI Request Filtering

New requests are checked for relevance by an LLM-based filter that rejects unrelated or nonsensical submissions before they reach the admin queue.

Admin Dashboard

View and manage incoming appointment requests with AI-flagged relevance indicators. Filter, approve, or reject submissions from a single interface.

Chatbot Receptionist

AI-powered chat widget on the website that greets visitors, answers common questions about the practice, and routes or books appointment requests.

Nearest Location Search

Location-based search so patients can find the closest registered practice using geolocation and radius filtering.

Multi-Provider AI Fallback

Five AI providers chained as fallbacks with a Supabase cooldown table so failed providers are skipped for minutes, surviving cold starts.

Engineering Challenges

The Agent Would Go Silent

The assistant would sometimes stop responding with no error or crash. This came from broken async/await chains, JSON.parse blowing up on messy LLM output, and code paths that ended without calling reply(). Fixed by wrapping every parser in try/catch with proper logging and adding a fallback response.

Treating Questions Like Form Fields

If someone asked "can you give me options?" the agent replied with canned form-filling text instead of answering. Every message was funnelled into the structured data extraction agent. Fixed by adding proper intent handling so queries get routed to the right place before falling back to form filling.

Running Out of Tokens Mid-Conversation

Multiple agents per message with full conversation history sent each time burned through the daily free-tier quota in a single afternoon. Fixed by capping history to recent entries, scoping the clash checker to one doctor, adding minimum gaps between AI calls, and making retry logic recognise daily caps versus normal rate limits.

Hallucinated Practice Details

The assistant answered questions about doctors with plausible but invented details. The practice information essay was falling outside the trimmed context window, so the AI filled the gap with fiction. Fixed by always fetching the practice essay fresh and explicitly instructing the AI to only answer from verified data.

Dates Like "9am Tomorrow"

People do not speak in ISO format. The database only accepts proper timestamp strings, so natural dates were failing on insert. Fixed by injecting the current date and time into the agent's context so the model always has a reference point for converting to clean ISO 8601 UTC strings.
