Overview

Kopano is a check-in and community app for small church fellowships. Somebody opens a check-in at the front of a room, everybody else marks themselves present from their phone — either by typing four digits or by scanning a QR — and the register writes one row per person per gathering. Between those two moments sit the parts that make it safe: a session window, a haversine distance rule, a nullable cancel column that behaves like a one-way switch, and a service-role key that never leaves the server.

The React 19 SPA and a separate /qr subapp talk to three Vercel serverless tiers — /api/self, /api/leader, /api/admin. Every route verifies the Firebase ID token against Google's signing keys and trusts only the email inside it, never anything the request body claims. Reads and writes go to Supabase PostgREST with the service-role key, which lives in exactly one place: the three api/*.js handlers, never in dist/. The twelve-page MkDocs Material documentation site walks through the architecture, the database, and every probe that was run against live data — including the honest list of what is still not enforced.

My Contributions

Three-Tier Serverless Dispatcher

Split the original /api/god monolith into /api/self, /api/leader, /api/admin, each with its own allowlisted function map and its own role gate. A request that guesses the wrong door is refused before the whitelist is even consulted, so no tier can borrow another's power.

Session + Check-in Engine

A leader opens a session with a four-digit PIN and an optional radius. Check-in matches (community_id, pin) against the cancel filter, checks the window against the server's clock, and runs the haversine against the session radius before writing. A second POST after the first has landed returns the original checked_in_at with already: true, backed by the unique (community_id, event_date, event_name, user_email) constraint.

QR Subapp

A separate /qr entry (built alongside the main SPA) that renders the session's QR so a member can scan and land straight on the check-in card. Same session checkin call, same tier, same rules — the two doors cannot diverge.

Community Roles & Join Codes

Join codes are six characters drawn from a visually safe alphabet (no 0, O, 1, I) via crypto.getRandomValues, checked against the table before writing. Admins can assign roles, remove members, and change the code, but cannot demote the only admin, remove the last member, or promote themselves into a fresh community that already has people.

Absence Notices in the Member's Own Words

Moved the reason from a five-value check constraint to free text, with the five words kept as UI suggestions only. A member can file a notice for a day with no session (rejected with a real reason, not filed under a blank), and a notice cannot undo a yes already recorded.

Firebase Auth Consolidation

Collapsed a duplicated initializeApp that was winning a bundler coin-toss for the session-storage key, added browserLocalPersistence so browsers that reject IndexedDB don't silently fall back to memory, and rewrote Auth.onChange to fire on a change of person and nothing else — killing the "keeps checking, keeps refreshing" loop.

Security Audit & Findings Doc

Eight findings, each dated and each verified by running code against the live Supabase project rather than reading it — from event being world-readable to /api/god rejecting every genuine Firebase token because of a JWT-segment bug. Every claim shows the probe that confirmed it.

Documentation Site

Twelve pages under MkDocs Material covering architecture, database schema, authentication flow, check-in and QR flow, feedback, onboarding, testing, user stories, and findings — with the honest "What is not enforced yet" section left in because pretending a gap is closed does not close it.

Hard-Won Lessons

RLS Off Is the Same as No Auth

Two tables — event and testimony — had RLS disabled while the four next to them were locked. Probing with only the anon key (which Vite inlines into the browser bundle) returned 1000 attendance rows and 242 testimonies to any visitor, and both tables accepted writes from that same key. Enabling RLS with zero policies closed the hole immediately.

A PostgREST Read Silently Truncated at 1000

An attendance query returned exactly 1000 rows with no error — PostgREST's default page size masquerading as a complete result. The fix is pagination, but the real lesson is that a "clean" answer can just be the first page of a much larger one.

Two Join-Code Generators Disagreed

The database default drew hex characters (which include 0 and 1) while the app's generateJoinId() drew from a visually safe alphabet that excludes them. So a brand-new community could be handed a code like C5EB14 that a person reading it aloud could never type correctly. Making create call the app generator is a two-line fix; the DB default stays as a safety net for hand-inserted rows.

PostgREST Answers Queries, Not DDL

Dropping the stale event_reason_check constraint from the live table cannot be done from the app — no psql, no CLI, no Management API credential. It has to be run by hand in the Supabase SQL editor, and the docs say so explicitly so the next person does not chase a phantom bug.

Every Firebase Re-Emit Felt Like a New Sign-In

onAuthStateChanged fires every time Firebase reloads the account, and pages that fetched or navigated in the listener were fetching or redirecting on every one of those. The rewritten Auth.onChange reports a change of person and nothing else — first settled callback always goes through, then silence.

Two Pages Answering the Same Fact in Opposite Directions

Every signed-in screen used to navigate to /login on a settled null, while /login bounced a session-holder straight back to /community. One reload became an infinite ping-pong. Now a null leaves the person where they are and the screen says "this browser holds no saved session" — with a link that only moves when they click it.

Key Features

Triple-Gated Check-in

A yes is only recorded when the PIN, the time window, and the haversine distance all agree. The radius is nullable and allow_any_radius overrides it; a derived near_required boolean so no page has to remember the rule.

One-Way cancel Column

A plain boolean default false is the one switch that decides whether a check-in counts. A session is only offered for check-in, only blocks another from opening, and only shows as live while cancel is false. Cancelling is one-way — the row keeps its history and is never reopened.

Service-Role Isolation

The Supabase service-role key lives in exactly three files under api/. It never appears in dist/, so the browser bundle cannot be picked apart to find it. Only one page (the testimonies screens) talks to PostgREST directly, and that is a deliberate trade-off documented in the architecture.

Firebase ID Token as Sole Credential

Every server route verifies the bearer token against Google's signing keys. The email the row is written under is the one inside the verified token — never anything the request body claims. A body that names user_email is silently dropped.

One-at-a-Time Session Lock

A session create is refused 409 when its window overlaps any un-cancelled session already standing on that community, so two leaders cannot hold two check-ins open at once — settled on the server, not by a page that might be looking at a stale list.

App-Wide Feedback Table

The only table not tied to a community_id. Any signed-in member may write; only an admin of at least one community may read. The write path takes the email from the ID token or leaves it null if the submitter unchecked "include my email"; the row survives the person.

Roster in One Read

AdminDashboard.roster() selects with users!inner(name, surname) so Postgres does the join, flattens the nested object, and orders by role then email. The screen never prints an address that isn't the reader's own — even though the row still carries one.

Audit Trail in the Docs

Every claim about what a rule does was checked by asking the live function with a real Firebase ID token. The docs show the exact request, the exact response, and how the probe data was cleaned up afterwards.

Architecture Decisions

Enforce Permissions in api/, Not in the Browser

Supabase RLS policies test auth.uid() against a Supabase-issued JWT — a Firebase token means nothing to them. So the rules live in the three Vercel handlers, which verify the Firebase token server-side and then query with the service-role key. That keeps the key off the browser and puts every rule in one reviewable place.

Direct PostgREST for the Testimonies Page

Testimonies paginate, search and export client-side, and every one of those fits a direct connection better than a serverless round trip. This is a deliberate exception to the "everything through a tier" rule, and it is written down in the same breath as the RLS gap it exposed.

Allowlisted Function Dispatcher Per Tier

Each endpoint carries its own whitelist of callable functions and its own role gate. Nothing outside the whitelist is even attempted, so an unknown action fails before any business logic runs. The tier map lives on the browser in src/page_functions/god.js; the enforcement is on the server.

Database Rules + Function Rules, Both Documented

The honest trade-off written down: rules in the request handler are easy to reason about and impossible to route around only as long as every path goes through it. Rules in the database hold whatever the client is, but forgetting one table is silent. The next pass is RLS with policies on the two tables a browser still writes to.

No Rate Limit Yet (Known)

A browser that guessed four digits by trying every combination hits /api/self as fast as its network allows. The only cost today is a wrong-PIN refusal per attempt. Vercel's per-function concurrency and the project's request quota stand in front of the worst case, but neither is a designed guard — the fix is documented and scheduled.
